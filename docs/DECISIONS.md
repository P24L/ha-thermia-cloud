## D1 — Name ✅

| What | Value |
|---|---|
| GitHub repository | `P24L/ha-thermia-cloud` |
| HA integration domain | `thermia_cloud` |
| Display name | **Thermia Cloud (unofficial)** — in `manifest.json`, `hacs.json` and the README title |
| Python package (inside `custom_components/thermia_cloud/client/`) | later extractable to PyPI as `thermia-cloud` |

**Why this name**
- `thermia` is taken by the existing HACS integration (`klejejs/ha-thermia-heat-pump-integration`). Two integrations with the same domain cannot be installed side by side, and we want to run both during migration.
- *Cloud* describes what it is (it talks to Thermia's cloud, not to the heat pump) and distinguishes it from the local/Modbus projects (`CJNE/thermiagenesis`, `ryckema/Thermia_itec`, `mdepa91/esphome-thermia`).
- It survives portal renames. *Thermia Online* has already been replaced by *MyThermia* once (2026-09-18).
- Checked 2026-11-17: no `thermia_cloud` (nor `thermia`) directory in `home-assistant/core`, `P24L/ha-thermia-cloud` is free, `thermia-cloud` is free on PyPI.

**Rejected:** `thermia` (domain clash), `thermia_online` (aging name), `mythermia` (brand-like, and the new API is unknown), `thermia_registers` (implementation detail), `thermia-ng` (meaningless in a year).

**Trademark:** "Thermia" is used descriptively and the display name carries *(unofficial)* so it cannot read as an official product. README carries a *not affiliated with Thermia / Danfoss* disclaimer. The icon is our own generic heat-pump drawing, **not** the Thermia logo.

## D2 — License and attribution ✅

- **GPL-3.0-or-later** for everything we write. The upstream projects (`klejejs/*`) are GPL-3.0.
- **The sign-in code is written from scratch** against the protocol description in `API-NOTES.md` §2 (OAuth2 authorization-code + PKCE against Azure B2C — the steps are dictated by the identity provider). **No upstream code is copied**, so nothing in `client/` is a derived work and no "or-later" relabelling problem arises (upstream declares plain `GPL-3.0`). Honest caveat: the protocol knowledge came from reading upstream code; keep the implementation independent (written from `API-NOTES.md`, not from the upstream source) and credit the project for what we learned.
- **Not a GitHub fork** — different architecture, a fork history would mislead. `NOTICE.md` and the README credit the upstream projects for the research and the years of work.
- Courtesy: open a discussion on `klejejs/ha-thermia-heat-pump-integration` announcing the alternative (roadmap P1.9; after P0.12).
- Not legal advice.

## D3 — One repository, two layers ✅

One repo, but strict layering so the pure-Python client can be extracted later:

```
custom_components/thermia_cloud/
  client/     no `homeassistant` imports, async, own tests
  catalog/    data (YAML + i18n JSON) and the loader
  …           HA glue (config flow, coordinator, platforms)
```

Reason for the split we do **not** replicate: upstream splits into a PyPI library plus an HA integration because HA *core* requires it. We are a custom integration; two repos would only double the release overhead. Extracting `client/` to PyPI is Phase 10 and only needed for a core submission.

## D4 — Localization: bundled snapshots + refresh on demand ✅

Requested by the maintainer; risk accepted 2026-11-17.

- Snapshots of Thermia's label texts (register / group / value names) are **committed** under `catalog/i18n/<culture>.json` — **all 16 cultures** (maintainer's call: it is cheap). Generated by `scripts/sync_localization.py` (maintainer runs it with their own credentials), filtered to `REG_*`, `COMP_*`, `REG_GROUP_*` and value names.
- **Refresh names** is a **button** (and nothing automatic): it fetches `/api/v1/localization/{culture}` (an authenticated request), stores the result in HA `.storage` and reloads the entry. There is **no weekly auto-refresh**.
- Language selection: see D16.
- **Risk:** the texts are Thermia's. They are short UI labels redistributed under GPL-3.0 without a licence from Thermia. Mitigation: only register/group/value labels, credit the source, remove on request.

## D5 — Data-driven entities + small curated catalog ✅

Structure, limits and types come from the cloud's self-description; meaning (unit, device class, defaults, safety) comes from a small YAML catalog. Unknown registers still work (generic entity, disabled by default). Details: `ARCHITECTURE.md`, `CATALOG.md`.

## D6 — Write policy ✅ (revised 2026-11-17)

Controlling the heat pump is the point of the integration — switch hot water, change the operation mode, tune the heating curve. Writing is therefore **on by default**:

- **Everyday controls** are enabled and writable: hot water on/off and mode, operation mode, the heating curve (main and per circuit).
- **Installer-level, set-and-forget registers** (min/max supply temperature, heating stop, circuit mode, intervals) and **unknown registers** are created **disabled**: opt-in, because a wrong value can hurt (a remote house can freeze) and dozens of extra entities are noise. Enabling uses the standard HA entity UI.
- The catalog decides per register via `default_enabled`. `risk: service` registers are exposed **read-only** (a sensor) unless a user override says otherwise (`kind: skip` means "no entity at all", a different thing).
- **Operation mode including `OFF`:** exposed like the upstream integration does, **without extra confirmation** (maintainer's decision 2026-11-17). The cloud's per-value `confirmation` key (the web app asks before changing the mode) is deliberately ignored.
- **Read-only mode** is an *opt-in* option (default off) for monitoring-only setups and for trying the integration out.
- **Write path** (details in `ARCHITECTURE.md` §3.3): validation against limits / visible enum values, per-installation lock, no debounce, errors raised to the caller, read-back with a `pending_value` attribute, queued writes are not errors. Read-only mode is implemented **before** any write platform exists (roadmap P5.4 first).

(The first draft disabled writes by default; that contradicted the purpose of the integration and was dropped.)

## D8 — Language of the repository ✅

English (README, docs, code, translations `en`), plus a Czech translation of the integration UI (`translations/cs.json`). A Czech README (`README.cs.md`) can follow later.

## D9 — Polling defaults ✅

Default 60 s (range 10–600 s), only the register groups that have at least one enabled entity, fast-poll 5 s for ~30 s after a write. Push is deferred (P10.7). Details: `ARCHITECTURE.md` §3.2.

## D10 — Unique IDs ✅ (frozen before v0.1)

- **Entity:** `"{installation_id}_{register_index}"`, plus `"_{suffix}"` where one register yields several entities — suffix = the **flag value** for status-flag binary sensors (`…_10002_1`, `…_10002_16`), or a fixed composite name (`…_waterheater`) for composite entities. All parts are strings.
- `registerIndex` is stable per register specification (e.g. 1020 = circuit-1 heating curve); `registerId` is the write id and may change with profiles. Verified unique across the 26 registers of one iTec profile; re-verify with more dumps (P0.4).
- **Config entry:** the token's `sub` (or `oid`) claim, falling back to the lower-cased e-mail (ARCHITECTURE §6).
- Changing these later forces unique-id migrations — do not change after v0.1.

## D11 — Scope ✅

In scope: Thermia cloud (classic API) account → installations → registers, read + write, multi-installation, multi-circuit.
Out of scope: local access (the DCM03 gateway has no open ports), other brands, Modbus (see related projects), HA core submission (stretch goal).

## D12 — Public from day one; private data stays out ✅

The repository is public from the first push. Maintainer-specific information (hosts, key paths, entity and automation names, the production rollout inventory) lives in git-ignored local notes files and `private/`. Public docs use generic wording. Test fixtures are anonymized (`scripts/anonymize.py`).

## D13 — Visibility is split into structural and value-based ✅

Structural conditions (other registers) decide at discovery whether an entity exists; value-based conditions and `disabledRegisterValue` make an existing entity `unavailable` at runtime. See `ARCHITECTURE.md` §3.1.

## D14 — Names: curated translations + collision pass ✅

Curated registers use our own short translated names; Thermia's labels fill the rest; the planner disambiguates collisions on one device; brackets are stripped only when they are a known unit. See `ARCHITECTURE.md` §4.3.

## D15 — Scope of v0.1 ✅ (2026-11-17)

- **Deferred:** WebSocket push (P10.7) · per-register override **editor** (decided 2026-11-17: not in v0.1; later, P10.8; cost in `UI-DESIGN.md` §4) · weekly auto-refresh of labels (**dropped**) · the `auth_failed` Repair (**dropped** — HA's reauth flow is the surface) · "Use push" option.
- **Kept:** all 16 bundled cultures · Refresh-names and Rediscover **buttons** (not options-flow fields) · reauth and reconfigure · diagnostics.
- No persistent notification from the config flow.

## D16 — Label language ✅

Option *Label language*: **Auto — follow the Home Assistant language** (default; falls back to English when Thermia has no text in that language), or pick any of the bundled cultures explicitly, English included. Changing it reloads the entry; entities the user renamed keep their name. (One-line change if the maintainer prefers English as the default.)
